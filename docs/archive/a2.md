# AgriSight — Compact, Lively, Farmer-First UI/UX Master Prompt

## Mission

Audit and improve the EXISTING AgriSight application.

Do NOT rebuild from scratch.
Do NOT remove working functionality.
Do NOT fake data or results.

The goal is:

> Make AgriSight simple enough for a farmer to understand immediately.

The interface should be:
- Minimal
- Compact
- Lively
- Friendly
- Calm
- Clear
- Fast
- Mobile-first
- Farmer-first

Principle:

```text
Show less.
Do more.
Hide complexity behind dedicated pages.
```

---

# 1. GLOBAL UI/UX RULES

Assume the user may:
- use a mobile phone
- be outdoors
- have limited technical knowledge
- prefer Bengali/Hindi
- want quick answers
- have limited time

Therefore prioritize:
- large readable text
- simple labels
- large touch targets
- clear icons
- one primary action
- short explanations
- strong visual hierarchy
- accessible local language

Avoid:
- dense dashboards
- too many cards
- too many numbers
- technical jargon
- giant tables
- long paragraphs
- competing buttons
- excessive animation
- excessive gradients/glassmorphism
- unnecessary decorative widgets

---

# 2. HOME/DASHBOARD — MAKE IT VERY MINIMAL

Home is a quick command center, NOT the entire application.

Home should answer only:

```text
How is my farm doing?
What needs attention?
What is the weather?
Can I scan my crop?
Can I ask AgriSight?
```

Keep only:

1. Greeting
2. Compact weather
3. Primary Scan Crop action
4. Important/current alerts
5. Compact AI Assistant access
6. Optional tiny real health summary

Remove/hide from Home:
- Full Field View
- Full field list
- Field boundaries
- Full heatmap
- Detailed scan history
- Large charts
- Detailed analytics
- Detailed crop tables
- Long recommendations
- Duplicate statistics
- Repeated health cards
- Technical AI information
- Large management panels

Move those to dedicated sidebar pages.

---

# 3. TARGET HOME LAYOUT

Use a compact structure similar to:

```text
Good morning, Farmer 🌱
Here's what needs your attention.

[ Weather ]
28°C • Partly Cloudy
Humidity 72% • Rain 20%

[ 🌿 SCAN YOUR CROP ]
Check crop health in seconds
[ Scan Now ]

[ ⚠ Important Alert ]
Disease risk increasing in Field 01
[ View ]

[ 🤖 Ask AgriSight ]
```

Do not turn every item into a giant card.

The Scan button should be the strongest action.

---

# 4. WEATHER

Keep weather because it is useful.

Show only:
- temperature
- condition
- humidity
- rain probability
- optionally wind

Do NOT put full forecast tables/charts on Home.

Detailed weather can live elsewhere.

---

# 5. ALERTS

Home should show only current/high-priority alerts.


Use:

```text

```

for the complete alert page.

# 9. SCAN PAGE — KEEP IT FOCUSED

The Scan page should be a dedicated tool.

Initial:

```text
Scan Crop

Take a clear photo of a leaf,
plant, stem, or fruit.

[ Turn On Camera ]
[ Upload Image ]
```

Camera:

```text
LIVE CAMERA

[ Capture ]

Camera Active ●
```

Preview:

```text
Crop Preview

[ Retake ] [ Analyze ]
```

Processing:

```text
Uploading image...
Validating crop...
Analyzing...
```

Then show only essential diagnosis information.

---

# 10. SCAN ACCURACY MUST REMAIN STRICT

Do NOT sacrifice accuracy to simplify the UI.

Maintain these rules:

- Non-crop images are rejected.
- Crop is never guessed.
- Tomato is never a default.
- Healthy is never a default.
- Confidence is never fabricated.
- Low-confidence images become UNCERTAIN.
- Invalid scans do not update field health.
- Invalid scans do not update heatmaps.
- Previous scan results cannot leak into a new scan.

---

# 11. SIMPLE SCAN RESULT

Farmer view:

```text
🌿 Crop Detected

Tomato

⚠ Possible Early Blight

Risk: Medium

What to do:
• Inspect nearby leaves
• Remove badly affected leaves
• Follow appropriate crop-care/IPM guidance

[ Save to Field ]
[ Ask AgriSight ]
[ Scan Again ]
```

Put advanced information behind:

```text
View Details
```

Advanced details may include:
- model confidence
- symptoms
- technical reasoning
- additional metadata

Do not overload the primary result screen.

```text
↓

↓
```

---

# 13. HEATMAP

The spatial map belongs in Fields.

Keep a compact preview:

```text
Spatial Health
[ map preview ]
[ View Full Map ]
```

Do not let the heatmap dominate the entire application.

The heatmap must use real field/scan data.

Never use random hotspots or fake health values.

---

# 14. ANALYSIS PAGE

Put advanced information here:

- scan history
- disease trends
- pest trends
- risk trends
- health history
- charts
- detailed statistics

This is for users who need more information.

Do not move this complexity back into Home.

---

# 15. COMPACT CARDS

Each card should answer ONE question.

Good:

```text
Weather
28°C
```

Good:

```text
Disease Risk
Medium
```

Bad:

```text
Huge card
8 metrics
3 charts
5 paragraphs
multiple buttons
```

If a card needs a long explanation, simplify it.

---

# 16. PROGRESSIVE DISCLOSURE

Show important information first.

Use:

```text
Disease Risk: Medium
[ Why? ]
```

Then expand to:

```text
Humidity high
Previous symptoms detected
Crop is flowering
```

Do not show every detail initially.

---

# 17. LIVELY WITHOUT CLUTTER

"Lively" means subtle feedback, not visual overload.

Use:
- button feedback
- hover states
- subtle transitions
- scan progress animation
- friendly icons
- smooth navigation

Avoid:
- bouncing everything
- constant movement
- particle effects
- giant animated backgrounds
- long page transitions
- distracting gradients

Animation must never slow interaction.

---

# 18. COLOR SYSTEM

Use restrained semantic colors:

```text
Green  = Healthy
Yellow = Attention
Orange = Warning
Red    = Critical
Neutral = Information
```

Do not make every card colorful.

Use color primarily to communicate state.

---

# 19. TYPOGRAPHY

Prioritize readability.

Use:
- large headings
- readable body text
- clear labels
- sufficient line height

Avoid:
- tiny text
- excessive uppercase
- condensed typography
- decorative fonts

Test Bengali and Hindi wrapping carefully.

# 25. HOME PERFORMANCE

Home must fetch only what it displays.

Home data should normally be limited to:

```text
User
Weather
Important Alerts
Small Health Summary
```

Do NOT fetch on Home:
- full field dataset
- full heatmap
- full scan history
- full analytics
- all crop history
- large image galleries

This must also improve loading speed.

Use:
- caching
- request deduplication
- parallel requests where appropriate
- lazy loading for heavy pages

Do not block the Home shell on secondary data.

---

# 26. LOADING UX

Render the Home shell immediately.

Use small skeletons for:
- weather
- alerts
- optional health summary

Scan and navigation should remain usable immediately.

Never leave the user staring at a blank screen.

---

# 27. ERROR UX

Keep errors simple.

Bad:

```text

```

```text

[ Try Again ]
```

Each feature should fail independently.
